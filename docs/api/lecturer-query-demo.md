# Lecturer demonstration — Phase 6A–6C query services

## Run locally

From the repository root in PowerShell, with the repository's dependencies already installed and Node 24 available:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\demo-backend-queries.ps1
```

Default output is a 26-line lecturer summary with five stages: request, validation/SQL, transaction results, batch results and final verification. It hides UUIDs, full SQL, full JSON responses and framework logs. Use the same command with `--verbose` for the original detailed trace:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\demo-backend-queries.ps1 --verbose
```

Both modes execute exactly the same database operations and original assertions. Normal mode displays only presentation lines after a successful run; if the test fails, it prints the captured diagnostic output and fails the command. Both presentation flags are restored afterward.

The execution-policy option applies only to this child PowerShell process; it does not change the user's saved policy. The runner selects the repository directory automatically and invokes the installed local Vitest entry point. It does not invoke Corepack/pnpm downloads, start Next.js or use hosted Supabase. The harness constructs its database connection exclusively from the disposable socket and explicit local settings, never from `.env.local` or developer database credentials. It restores its console-output flag afterward. No package/configuration changes or new dependencies are required.

This is an **internal service demonstration**, not an HTTP/API deployment or a V2 ingestion adapter. No Postman/curl URL or public route exists. Runtime production services and Jason's modules remain unchanged.

## What to show

The runner enables console output from `tests/demo/backend-queries.demo.test.ts`. The same test runs quietly in the normal full test suite. The walkthrough below describes the expanded `--verbose` trace; normal mode summarizes the same verified results.

1. **Local fixture preparation:** a fresh PostgreSQL-compatible WASM database loads the existing SQL scripts only into disposable memory. The actual `pg` driver connects to a newly allocated loopback socket. The existing synthetic producer helper and grouped writer prepare two batches; persistence is background setup, not the focus of this presentation. All displayed values are invented synthetic data. UUIDs and database timestamps may vary per run.
2. **Transaction page 1:** show an internal `transactions.list` request with `date_from=2026-09-02`, `date_to=2026-09-03`, `status=VALID`, `limit=2`. The real filter parser prints the validated values. The service repeats validation internally.
3. **Test scope and actual query:** the injected, fixed synthetic actor/organization scope contains only the fixture batch IDs. The database wrapper prints the SQL generated by the unchanged service and its separate parameters. Look for the scope predicate, accepted-status predicate, date predicates, native date/UUID ordering and `limit + 1` lookahead. The wrapper executes that exact SQL, not a reimplementation.
4. **Audit gate and returned DTOs:** the injected test audit acknowledges before the service returns. Show the quoted monetary value `"9007199254740993.123456789"`, leading-zero reference `"00017"`, and real JSON `null` in unavailable debit/credit/balance and optional posting-date fields. No floating-point conversion or replacement of NULL with zero occurs. The fixture with source amount zero returns the exact canonical string `"0"`; zero is distinct from NULL.
5. **Transaction page 2:** pass the first page's opaque test cursor with the same filters. Its registry verifies the complete binding; the console shows the anchor date/UUID. The generated SQL uses tuple `<` continuation, not OFFSET. The second page contains the remaining one of the three VALID records, with no duplicates, and `nextCursor: null` marks the end. Two first-page rows share the same canonical date, exercising the UUID tie-break.
6. **WARNING acceptance:** an additional filtered query returns two WARNING records. One is a retained duplicate warning and one lacks a reference. WARNING remains accepted; neither query returns REJECTED evidence.
7. **Batch list and lookup:** list by the parent persistence-attempt UUID, then retrieve the main batch by its individual database UUID. Show ACTIVE, received 6, VALID 3, WARNING 2, accepted 5, REJECTED 1; warning summaries contain 2 issues (1 technical, 1 business). The other batch is COMPLETED_EMPTY with accepted 0 and rejected 1. A parent attempt is not the same entity as an ingestion batch. Counts do not expose rejected-row payloads or raw validation issues.
8. **Fail-closed guards and cleanup:** the test demonstrates that absent mandatory dependencies and an unrecognized synthetic context execute no SQL. The test closes the pool/socket and discards the in-memory database in `finally`, including on failure.

Five actual read queries and five test audit acknowledgements are asserted. Test failures return a nonzero runner result; the console output is backed by executable checks of values, page membership, counts and execution order, not just explanatory print statements.

## Security explanation

All normal service calls receive the mandatory scope resolver, cursor verifier/issuer and audit interface. These dependencies are visibly **TEST ONLY**:

- The resolver recognizes only the harness's fixed context object and returns fixture IDs. It verifies no JWT, session, real membership or role policy.
- Cursors use an in-memory registry with exact binding comparisons, not signatures, expiry, production storage or replay protection. This is not Jason's secure cursor implementation.
- Audit callbacks return the required acknowledgement for the demonstration; they do not implement a durable protected audit sink. A printed acknowledgement proves invocation and ordering only.
- The `server-only` marker is mocked in Vitest, matching existing integration tests. The actual mandatory security interfaces are still called and asserted. Production package guards and service source are unchanged.

The runtime order is request → validation → synthetic scope → parameterized SQL → service projection/cursor handling → **test audit acknowledgement** → returned DTO response. Audit comes before response release, as the existing service requires. The initial validation print is an explicit call to the same parser; it is not a new instrumentation hook inside production code.

This demonstration is evidence of backend query behavior with synthetic dependencies. It is not evidence that production authentication, tenant ownership, authorization policies, secure cursors or durable auditing are implemented. Those integrations remain Jason's responsibility and block public exposure.
