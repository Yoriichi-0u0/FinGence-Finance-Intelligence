Each run creates a uniquely named temporary cluster, binds only 127.0.0.1 on an ephemeral port, initializes empty storage and stops it in `finally`. It never reads application database URLs or environment files. It never connects to hosted Supabase or resets an existing database. The successful stopped cluster remains at `C:/Users/celes/AppData/Local/Temp/fingence-db01-1iZ4TQ` for investigation; this is disposable benchmark storage, not a user database.

Fixture date generation uses fixed seed **20261027**. Financial-record and batch IDs, counts, dates, money and lineage reproduce across variants. Warning issue primary keys and default creation timestamps are generated by PostgreSQL; semantic data is equivalent, but those incidental values and physical index layout are not byte-identical. Grouped probe identities/timestamps are also naturally generated by the unchanged writer.

Each fixture has 1,000 populated batches, 20% WARNING rows with one correctly linked issue each, technical/business issues, MYR/USD/SGD/NULL currencies, all three monetary bases and both canonical-date bases. Monetary literals stay native NUMERIC; `9007199254740993.123456789` is verified as exact text and unavailable balance remains NULL. Batch counters derive from fixture children; no REJECTED financial rows exist. Native checks verify row counts and accepted-status/issue consistency. Existing regressions verify wider cursor, count, provenance, NULL, atomicity and rejection-exclusion behavior.

Each variant reloads the equivalent fixture, runs ANALYZE and adds at most one candidate index. SQL and bind values are captured directly from the existing service builders, including their projections, accepted-status predicates, lookahead limit and real lateral warning summary. Test-only trusted scope/cursor adapters select cases; native timing then executes the captured SQL directly. Service projection, authorization, audit storage and cursor signing are outside the timed read path. This introduces no authentication or HTTP implementation.

## Plan evidence and index comparisons

Three benchmark-only indexes were compared individually against the original schema:

| Variant | Indexed columns | Added index bytes at 100,000 records | Broad transaction list median / p95 ms | Grouped median / p95 ms |
| --- | --- | ---: | ---: | ---: |
| Baseline | Existing indexes only | 0 | 4.159 / 5.088 | 121.619 / 145.613 |
| transaction_order | financial_records(canonical_date DESC, id DESC) | 6,012,928 | 5.161 / 6.332 | 184.620 / 213.576 |
| batch_order | ingestion_batches(created_at DESC, id DESC) | 65,536 | 5.860 / 7.845 | 191.303 / 220.309 |
| scoped_order | financial_records(batch_id, canonical_date DESC, id DESC) | 7,118,848 | 6.207 / 7.613 | 177.616 / 207.657 |

Observed grouped throughput was 542, 523 and 563 rows/second for these candidates. Their grouped median differences versus baseline were +51.8%, +57.3% and +46.0%. These are measured run differences, **not proven causal index overhead**: unrelated detail reads also slowed, variant order was fixed, and physical layout/background activity may differ. At smaller sizes write differences varied in sign/magnitude. Do not turn these percentages into production capacity forecasts.

Verified plan observations:

1. **Global transaction ordering reduces broad-scope scan work.** At 100,000 records/1,000 IDs, the [baseline list plan](2026-10-27T05-45-05-445Z/100000-baseline-1000-transaction_list.json) uses the existing date index plus incremental sort: 309 rows emitted by the scan, 300 shared buffer hits, 0.799 ms execution. The [transaction-order candidate](2026-10-27T05-45-05-445Z/100000-transaction_order-1000-transaction_list.json) uses its new index without sorting: 51 scan rows, 52 hits, 0.266 ms execution. These are individual EXPLAIN executions, separate from the 20-run latency samples. Broad continuation hits fell from 264 to 53, with execution 0.642 to 0.411 ms. The client median did not improve, so the plan benefit warrants follow-up rather than immediate migration.
2. **Batch warning aggregation dominates the measured batch-page work.** The [baseline broad batch list](2026-10-27T05-45-05-445Z/100000-baseline-1000-batch_list_warning_summary.json) executes in 10.869 ms with 16,520 hits. It scans 100 financial records for each of 51 lookahead batches and performs 5,100 issue-index probes. The lateral Aggregate averages 0.195 ms over 51 loops, approximately 9.945 ms of repeated aggregate work. This is a workload scaling cost, not evidence of incorrect results or permission to change the summary contract.
3. **Batch ordering alone does not remove that aggregation cost.** The [batch-order plan](2026-10-27T05-45-05-445Z/100000-batch_order-1000-batch_list_warning_summary.json) changes the 1,000-row batch sequential scan/top-N sort to 51 indexed batch rows. It still performs 5,100 issue probes and records 16,550 hits. Client batch-list median was 25.305 ms versus baseline 14.930 ms. The candidate addresses a small page-selection component in this 1,000-batch fixture.
4. **Scoped ordering helps some selective predicates without proving an overall win.** The [single-batch continuation plan](2026-10-27T05-45-05-445Z/100000-scoped_order-1-transaction_continuation.json) uses the candidate to reduce bitmap index rows from 100 to 55 and hits from 102 to 58; it still sorts. The single-batch first page retains the existing batch index, and broad pages retain the existing date index. Keeping batch_id first cannot directly produce the required global date/UUID ordering across arbitrary batch arrays.
5. **No measured disk spilling.** All final EXPLAIN roots report zero shared reads and zero temporary reads/writes. This confirms warmed shared-buffer observations, not zero storage I/O during ingestion or cold-cache operation. Sorts remained in memory; baseline broad transaction incremental-sort groups peaked at 41/43 KiB. Thirty plans included sequential scans, all on ingestion_batches; no financial_records sequential scan was selected in this matrix. A sequential scan of 1,000 batch rows is not itself a defect.

Every plan uses `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` and retains SQL/parameters. [plan-summary.json](2026-10-27T05-45-05-445Z/plan-summary.json) extracts scans, buffers, ordinary and incremental sorts. Index sizes are captured before grouped probes. [manifest.json](2026-10-27T05-45-05-445Z/manifest.json) records SHA-256 hashes for raw artifacts and relevant sources.

## Verification, failures and limits

- Existing API/persistence/grouped integration suite plus fixture regression: **20 files passed, 466 tests passed, one intentional native-matrix skip** outside the isolated launcher. The prior existing suite accounts for 465 tests; the extra passing test checks deterministic fixture generation and size rejection. The successful native launcher separately passed both benchmark tests.
- Next route type generation and `tsc --noEmit --incremental false` passed. Targeted ESLint and Git whitespace checks passed. No dependency, lockfile, production migration or application behavior change was required.
- Initial sandbox initialization failed on a WAL-file rename; local elevated execution resolved it. Sandbox Vitest initially failed before tests on temporary-file renames; its elevated run passed. Corepack could not reach the registry; the installed Node test/typecheck binaries were used directly.
- An initial probe cleanup deleted warnings before their records in separate transactions, correctly tripping a deferred check. Benchmark cleanup was fixed to delete the entire probe group in one transaction; application code was unchanged.
- A preliminary matrix timed out at 120 seconds while loading the 100,000-row scoped candidate. Its partial directory `2026-10-27T05-38-20-851Z` is **not the report dataset**. A fresh run used a 600-second fixture-load allowance, restored 120 seconds for reads, and completed all variants; the final scoped load took 20.828 seconds. The timeout was not consistently reproduced and its cause is unverified.
- Artifact checks found files missing during the environment transition. Benchmark sources and the pre-existing architecture review were restored from their original recorded patches. Final artifacts were rechecked for completeness; the successful directory contains every referenced plan. No deliberate deletion or edit of the original review was part of DB01.

Limitations: one local machine/run, fixed variant order, warm cache, one client, only 20 samples for p95, random database-generated warning IDs, no concurrency/lock-contention profile, cold-cache measurements, WAL-byte measurement, index-build timing, recovery test or hosted-schema verification. No OS CPU/memory/I/O telemetry was captured, so timing drift and the preliminary timeout cannot be attributed to a specific host cause. Fixtures use constant large exact money and batch-correlated warning/currency distributions; they are valid stress fixtures, not a model of real financial frequency or selectivity. Source lineage remains synthetic. The benchmark is not an authorization implementation or production throughput guarantee.

## Publication integrity follow-up

Source-hash verification exposed CRLF working-tree versus LF Git-blob differences in eight existing source files. DB01 now uses the shared `scripts/db01/integrity.mjs` hash implementation for manifest generation and verification: raw artifacts retain byte-exact SHA-256, while `crlf-to-lf-v1` source hashing removes only CR bytes immediately before LF. The manifest records both conventions explicitly. No application source, migration, benchmark measurement or raw plan was changed. `scripts/db01/verify.mjs` verifies either working files or actual staged Git blobs. A focused regression checks LF/CRLF equivalence and rejects changed artifacts, changed source content and unsupported conventions. This publication fix does not require another PostgreSQL benchmark run.

Publication follow-up verification passed: all 389 original artifact hashes remained unchanged, all 14 referenced source hashes verified with the documented convention, focused integrity/fixture tests passed (3 passed; native matrix intentionally skipped), and TypeScript plus targeted ESLint checks passed. The native benchmark was not repeated because its SQL, synthetic fixtures and measurements were unchanged.

## Recommendations and next work

**Verified:** the current indexed transaction queries handle the measured fixture sizes without financial-record sequential scans or temp spills; the broad batch warning summary performs substantially more repeated work than a transaction page. The transaction-order index reduces scan/buffer work in broad-page plans.

**Proposed:** repeat an interleaved or randomized baseline/candidate experiment with repeated baselines, stable host conditions, larger batches and realistic warning/selectivity distributions. Prioritize the global transaction-order candidate for that experiment, then assess whether write/storage costs are justified by an end-to-end improvement. Defer the batch-order candidate until larger batch cardinality makes page selection significant. Defer scoped ordering until representative selective scopes demonstrate consistent benefit. None is recommended for production adoption from this run alone.

A separate future investigation may compare equivalent warning-aggregation SQL on the already selected page and profile the sequential grouped writer's round trips. Any service/query optimization must preserve accepted-only storage, exact money/NULL/date meanings, lookahead/cursor order and whole-group atomicity and requires review under the original task boundaries. No cache, summary rewrite, bulk-writer replacement, RBAC or HTTP work was implemented.
