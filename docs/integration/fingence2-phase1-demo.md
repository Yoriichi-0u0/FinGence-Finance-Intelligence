# FinGence 2.0 Phase 1 — no-login connected synthetic demo

One action turns a bank statement and a cash-account general ledger (plus an optional bank
history) into one verified **processing context**. Overview, Data, Transactions, Reconciliation,
Analytics, Anomalies, Forecasting, Reports and Finance Q&A all read that same context.

## How to run

- **Hosted (Vercel) or `pnpm dev`:** open `/data`, choose **Use synthetic sample documents** (or
  your own CSVs in the same layouts) and press **Process Financial Documents**. No sign-in.
- **Local authenticated stacks** (`pnpm poc:dev`, M3/M5 flags): unchanged. Those pages keep their
  server-backed, audited workspaces and `/data` keeps the original C1 page. The browser demo is
  disabled there so the two modes never mix on one page (`lib/server/demo/mode.ts`).
- **Original C1 ingestion page:** `/data/c1` (not in the navigation).

## Why no sign-in is safe here (R1)

The demo never calls a server API and never touches the local database. Documents are read and
processed in the visitor's browser with the same pure functions the authenticated server path
uses; only the input documents are kept, per browser tab, in `sessionStorage`. Every existing
security check, session, tenant, role and audit control is unchanged. The 69 Production isolation
probes still block every experimental page and API, and `/finance-questions`, `/admin` and
`/ai-ingestion` remain 404 in Production.

A **localhost guest harness** (auto-provisioned synthetic Finance session for the authenticated
local stack) was investigated and deferred: it would need a server-side bootstrap that creates
an organization, an account and a session without credentials. That is an authentication change,
and the browser demo already removes the sign-in burden for synthetic demonstrations. If built
later it must be loopback-only, refuse `NODE_ENV=production`/`VERCEL`, use a fixed synthetic
organization, be auditable, and never be reachable from the hosted app.

## The processing context

`lib/demo/pipeline.ts` (`fingence-processing-v1`) runs eight stages. Each records its checks and
one decision: **AUTO_ACCEPTED** (independently verified), **QUARANTINED** (ambiguous, inconsistent,
missing or unsupported; never treated as fact) or **UNAVAILABLE** (the input cannot support it).

| Stage | What happens | Gate |
| --- | --- | --- |
| Identify | Role from exact column signature: bank statement, cash-account ledger, bank history | Exactly one bank statement and one ledger; evaluation/ground-truth files and duplicates quarantined |
| Extract | Shared normalizer (`lib/poc-reconciliation/engine.ts`) and history reader | Unique IDs, ISO dates, MYR, sign conventions on every row |
| Interpret | Scope (business, month, currency) and configured cash conventions | Bank and ledger scope must agree |
| Verify | A second parser (`parseSource`) re-reads the bank; ledger Debit − Credit re-summed from raw CSV; history month must equal the statement | Any disagreement quarantines the documents (or only the history) |
| Reconcile | Deterministic matcher, then `readReconciliation` re-validates the snapshot | Exceptions (bank only, ledger only, amount, duplicate, reference) quarantined, never cleared |
| Analyse | Exact-cent cash totals; `detectAnomalies` | Analytics total must equal the reconciled bank movement; candidates quarantined for review |
| Forecast | `forecastBusiness` six-month mean with rolling backtests | Only with ≥ 7 consecutive verified months; otherwise the engine's own refusal |
| Report | Management summary, JSON evidence, printable page | Same figures and source fingerprints |

The **processing ID** is a SHA-256 over the pipeline version and each accepted role and source
fingerprint: the same documents always give the same ID, in any order. Processing new documents
clears the previous context first, so a failed run can never leave stale results on screen.

## What is real, deterministic, simulated, precomputed or future

| Category | Items |
| --- | --- |
| **Real, computed in the browser** | CSV parsing, SHA-256 fingerprints, role identification, normalization, independent verification, reconciliation, totals, anomaly rules, forecast and backtests, summary, Q&A answers |
| **Deterministic rules (not AI)** | Schema recognition, cash conventions, matching, anomaly rules, six-month-mean baseline, keyword-routed Q&A |
| **Simulated** | Nothing is simulated in the demo path. Live model interpretation is not used and not claimed |
| **Precomputed / fixed** | Only the public sample documents in `public/demo/` (fictional, generated by `scripts/generate-demo-documents.mjs`, pinned by `manifest.json`) |
| **Future work** | Backend jobs, persistence, model-assisted schema inference, cross-source canonical records (see the architecture note) |

## Limitations

- Supported inputs are the PoC bank statement, cash-account ledger and normalized bank history
  layouts, one business, month and currency per statement pair, MYR only.
- Persistence is per browser tab; there is no account, sharing or audit trail in the demo.
  Persisted human exception review exists only in the authenticated local workflow.
- No accounting classification: bank receipts and payments are not revenue or expenses, and no
  profit or ratios are shown.
- The printable report uses the browser's print-to-PDF; the server PDF renderer remains local-only.
